Stage 1 of 5

Setup review

Before any content is built, an agent reviews the Canvas sub-account and course shell against the programme’s requirements, so problems are caught while they are still cheap to fix.

Where judgement staysThe agent flags deviations; a person decides which are genuine problems and which are intentional, like an extended navigation on an orientation course.

The task

The setup-review agent reads the live configuration and the template pages, and compares both against the programme’s documented standards: the approved theme version, the six-item navigation, the grading scheme, and the markup the template pages should use.

It changes nothing — the output is a findings list, ordered by how expensive each issue becomes if it reaches the build stage.

Sample output — the review
  • ✓Theme current. CSS and JS both v2.3 — matches the programme standard.
  • ✓Grading scheme matches. FCA standard scheme applied at course level.
  • !Two heading styles in use. Three template pages carry manually-styled H2s instead of the themed class — these would propagate into every built page.
  • !Navigation shows 11 items; standard is 6. Files, Outcomes and three tool links are visible to learners.
  • !Module locks not set. All modules currently open; the programme releases Module 1 only at launch.

Canvas build

An agent converts the approved storyboard into the programme’s Canvas HTML — pages, assessments and discussions in the right module — behind a dry run, with a reload to verify every page it builds.

Where judgement staysThe dry run is approved by a person, and anything ambiguous in the storyboard — a missing image, an unclear activity — is queried, never guessed.

The checks
  • ✓Dry run first. The agent lists every page, assessment and discussion it will create — nothing is written until the plan is approved.
  • ✓Copy is verbatim. Authored content is checked byte-for-byte against the storyboard; the build never paraphrases.
  • ✓Verified by reload. Each built page is reloaded and read back to confirm the markup survived Canvas’s editor.
  • !Queried, not guessed. The storyboard’s glossary note (“term modal: categorical data”) had no approved definition — raised with the author instead of invented.

Stage 3 of 5

Video placement

Course videos live in Wistia and are listed in a media register kept separately from the storyboards. An agent matches each row to its video, retrieves the embed code and transcript, and places both into the correct page markup.

Where judgement staysA register row whose title doesn’t match the video it points at is flagged for a person — a mislabelled video placed “successfully” is worse than one left unplaced.

Stage 4 of 5

Feedback actions

QA feedback arrives as tickets linked to course content. An agent gathers the outstanding tickets, checks each against the approved storyboard, and separates actionable corrections from items needing clarification — then applies approved fixes behind a dry run.

Where judgement staysA ticket that contradicts the approved storyboard isn’t a correction — it goes back to QA with the discrepancy named, not silently “fixed”.

Stage 5 of 5

Build review

Before anything is published, an agent compares every completed page with the approved storyboard and the build standards: content accuracy and order, components and media, accessibility details, navigation, completion requirements, and links — including whether internal links survive course cloning.

Where judgement staysThe agent produces the evidence; the decision to publish is a person’s. Flagged items are investigated, not auto-resolved.

Sample output — the review
  • ✓Content matches, in order. Every storyboard element is present, verbatim, in sequence.
  • ✓Accessibility details present. Alt text on the image, transcript with the video, one H1 per page.
  • ✓Clone-safe links. Internal links use course-relative paths, so they stay valid when the course is cloned for the next presentation.
  • !Completion requirement missing. Page 3.4 has no “mark as done” requirement; the module’s standard requires one.
  • !External link redirects. The chart-checklist source link returns a redirect — update to the final URL before publishing.
The checks — and the handover

The review ends as a report, not a publish action. The two flagged items above are investigated, fixed through the feedback workflow, and re-checked — then, and only then, a person publishes the module. The time the agents recover is spent here: deeper checks on content, accessibility, navigation and functionality than a compressed schedule would ever have allowed.
